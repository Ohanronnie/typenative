# TypeNative Design Audit

## 1. Purpose

This audit records the contradictions, factual errors, undefined semantics, and
scope problems found in the source documents and maps each one to the canonical
resolution. It is explanatory; the [language specification](language-spec.md)
and [compiler architecture](compiler-architecture.md) are authoritative.

The source documents remain outside the repository and were not edited.
The implementation-level inventory of compiler-known names is maintained in
[`compiler-magic-audit.md`](compiler-magic-audit.md); entries that are not
fundamental language mechanisms remain explicit migration obligations there.

## 4. Syntax and source model

| #   | Source issue                                                                                                                                                          | Why it fails                                                                                            | Canonical resolution                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 9   | The `.tn.ts` source suffix identifies files as TypeScript even though the grammar adds foreign keywords and operators.                                                | Editors and tools would select the wrong grammar and users would expect TypeScript compatibility.       | Use `.tn` exclusively and provide no compatibility alias.                                                                   |
| 10  | SWC is selected as the parser while examples contain `struct`, `match`, `unsafe`, `throws`, raw/reference type syntax, compile-time declarations, and foreign blocks. | SWC parses ECMAScript/TypeScript grammar, not an independently extended language.                       | Use Logos plus a TypeNative recursive-descent/Pratt parser and a Rowan lossless CST.                                        |

| 13  | There is no lexical specification, semicolon rule, operator precedence, or recovery contract.                                                                         | Parser, formatter, and examples could disagree on basic syntax.                                         | Provide normative EBNF, required semicolons, explicit precedence, UTF-8/XID rules, and recovery architecture.               |
| 14  | Optional fields are rejected on the claim that native memory cannot represent absence.                                                                                | A tagged or niche-optimized optional has a fully static layout.                                         | `field?: T` and `T \| undefined` are the same optional type.                                                                |
| 15  | General unions are promised as tagged values without construction, normalization, overlap, narrowing, ABI, or layout rules.                                           | Structurally overlapping union members cannot be implemented coherently from the described type system. | Restrict union syntax to optional values; use nominal enums for all other sum types.                                        |
| 16  | Intersection types are described as merged structs despite nominal structs and layout identity.                                                                       | Merging nominal layouts silently changes identity, visibility, and field conflicts.                     | Exclude intersection value types; combine interface constraints with `+` in `where` clauses.                                |
| 17  | Object literals are both dynamic-looking values and fixed structs, with partially specified spread behavior.                                                          | An uncontextualized object has no nominal type or stable layout.                                        | Object literals require an expected struct type; unknown fields and all spread forms are rejected.                          |
| 18  | Mutability examples use inconsistent forms and mutate through bindings described as immutable.                                                                        | Borrow checking needs one source-level rule for mutable places.                                         | `const` forbids reassignment and mutable borrowing; `let` permits them; fields may be `readonly`.                           |
| 19  | Function overloads are mixed with union implementations and generic inference.                                                                                        | Exact overload resolution, implementation compatibility, and ambiguity are undefined.                   | One function or method per name; use generics and interface constraints.                                                    |
| 20  | The generic `max` example uses comparison without a declared capability.                                                                                              | The body is not valid for every `T`.                                                                    | Generic operators require explicit standard-interface constraints.                                                          |
| 21  | General executable decorators are described without a bytecode, interpreter, capability, determinism, caching, or hygiene model.                                      | The feature is a second language runtime inside the compiler and conflicts with restricted I/O claims.  | Support compiler-defined attributes only; source code cannot execute during compilation or generate declarations.           |
| 22  | Class syntax, struct syntax, interface syntax, and method syntax have no shared formal grammar.                                                                       | Independent implementations could accept different languages.                                           | The EBNF defines every declaration and member form used by examples.                                                        |
| 23  | General JavaScript equality and coercion expectations are not addressed.                                                                                              | Native numeric and object semantics cannot safely inherit loose coercions.                              | Provide strict equality only, no loose equality, and no implicit numeric conversions.                                       |
| 24  | String and character literal roles are not separated.                                                                                                                 | A systems language needs an exact scalar versus UTF-8 text distinction.                                 | Double-quoted strings, single-quoted Unicode scalar characters, and typed template strings have distinct grammar and types. |

## 5. Types and numerics

| #   | Source issue                                                                                                                | Why it fails                                                                                          | Canonical resolution                                                                                              |
| --- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 25  | The plan equates C `int` with a 64-bit platform integer.                                                                    | Common 64-bit ABIs still use a 32-bit C `int`; the statement is factually wrong.                      | `number` is exactly `isize`; C interop uses explicit `c_*` aliases.                                               |
| 26  | `number` is called platform native without a precise relation to pointer width or FFI.                                      | Layout, ranges, Node conversion, and cross-compilation remain ambiguous.                              | `number` is a language alias of pointer-width signed `isize` and maps to JavaScript `bigint` on supported hosts.  |
| 27  | Fixed-width 128-bit integers are labeled platform-dependent.                                                                | Their width and range are fixed even if a target lowers operations to helper calls.                   | Define exact 128-bit integer semantics independent of instruction selection.                                      |
| 28  | Target-conditional half and extended floating types appear in the core type table.                                          | Source validity would depend on backend target capability.                                            | Core floating types are `f32` and `f64`; both have fixed IEEE semantics.                                          |
| 29  | Decimal literals without context are rejected as ambiguous even though the language advertises inference.                   | Simple numeric code becomes unnecessarily annotation-heavy.                                           | Decimal literals default to `f64`; integer literals default to `number`; context or suffix may override.          |
| 30  | No implicit-conversion policy accompanies mixed arithmetic and FFI examples.                                                | Implementations could silently truncate, promote, or reject differently.                              | No implicit numeric conversions; use exact `from`, fallible `tryFrom`, and explicit arithmetic families.          |
| 31  | Overflow panics in one profile and wraps in another.                                                                        | Program results and security behavior change when optimization is enabled.                            | Ordinary arithmetic remains checked in all profiles; wrapping, saturating, and checked alternatives are explicit. |
| 32  | Division, shifts, narrowing conversion, float-to-int, and indexing failure are unspecified.                                 | Overflow policy alone is incomplete.                                                                  | Specify checked division, shift counts, conversions, and bounds; invalid operations abort through panic.          |
| 33  | String indexing and slicing semantics are not defined.                                                                      | UTF-8 text cannot use byte indexing safely.                                                           | Reject text indexing; expose scalar iteration, byte views, and checked UTF-8-boundary slicing.                    |
| 34  | Type inference is described as Hindley-Milner plus subtyping, effects, classes, and unions without an algorithmic boundary. | Principal types are not generally available under that combination.                                   | Use local bidirectional inference with explicit public signatures and declared constraints.                       |
| 35  | Structural and nominal typing are both assigned to declared structs.                                                        | The same type cannot simultaneously derive identity only from declaration and only from member shape. | Structs, classes, enums, and interfaces are nominal; interface conformance is explicit.                           |

## 6. Ownership, memory safety, and classes

| #   | Source issue                                                                                                            | Why it fails                                                                                          | Canonical resolution                                                                                                                                   |
| --- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 36  | References are called safe and non-null while lifetime checking is absent.                                              | A non-null pointer can still dangle or alias mutable storage.                                         | Mandatory affine ownership, non-lexical borrow checking, and lifetime validation make safe references valid.                                           |
| 37  | Safety is opt-in by source file and all other files are unsafe by default.                                              | Safe callers cannot trust signatures from unchecked files, and data can cross file boundaries freely. | Safety is the language default everywhere; unsafe permission is lexical and operation-specific.                                                        |
| 38  | Lifetime checking is version-staged after programs have already relied on unchecked behavior.                           | Introducing ownership later changes the meaning of nearly every API.                                  | Ownership, borrowing, and lifetime syntax are part of the canonical language from the start.                                                           |
| 39  | RAII and deterministic destruction are promised without move rules, initialization analysis, or cleanup edges.          | The compiler cannot know which values still own resources.                                            | MIR models moves, partial moves, initialization, drop flags, and every normal/error cleanup edge.                                                      |
| 40  | `Drop` has no restrictions on throwing, moving fields, recursion, or async behavior.                                    | Cleanup could fail recursively or leave partially destroyed values.                                   | `Drop` cannot throw, suspend, move fields, or be called directly.                                                                                      |
| 41  | Panic and release assertions are described independently of destruction.                                                | It is unclear whether abort unwinds or leaks observable resources.                                    | Panic always aborts without unwinding; recoverable errors are the cleanup-preserving path.                                                             |
| 42  | `Rc`, `Arc`, and references mention thread safety but no `Send`/`Sync` type system exists.                              | The compiler cannot reject cross-thread captures or shared non-thread-safe data.                      | Compiler-checked `Send` and `Sync` constraints govern threads and detached tasks.                                                                      |
| 43  | Smart pointers are placed in inconsistent standard-library modules.                                                     | Imports and ownership responsibilities are unclear.                                                   | `Box`, `Rc`, `Arc`, and `Weak` live in `std/alloc`; synchronization primitives live in `std/sync`.                                                     |
| 44  | Classes are described as structs with methods while inheritance, identity, allocation, and aliasing are left undefined. | TypeScript class expectations require an object model, not simple syntax sugar.                       | Classes are heap-allocated, uniquely owned handles with identity, single inheritance, and virtual dispatch.                                            |
| 45  | Shared class references would require either hidden retention or unchecked aliases.                                     | Both conflict with visible cost and safe ownership.                                                   | Sharing requires explicit `Rc`, `Arc`, or `Weak`; ordinary assignment moves.                                                                           |
| 46  | Dynamic dispatch is mentioned through interfaces without witness layout or conformance rules.                           | Code generation and coherence cannot be implemented.                                                  | Explicit conformance selects immutable witness tables; dynamic values carry data and witness pointers.                                                 |
| 47  | Class overriding rules and destructor dispatch are absent.                                                              | Base calls and deletion through a base owner may call the wrong implementation.                       | Methods are virtual by default, `override` is required, `final` opts out, and destruction is virtual from the base.                                    |
| 48  | Class downcasting and runtime type information are not bounded.                                                         | Full reflection could be accidentally required by `instanceof` behavior.                              | Store compact ancestry descriptors supporting only `instanceof` and checked `as?`; no field or method reflection.                                      |
| 49  | Packed structs are presented as normal field-accessible values.                                                         | Taking aligned references to packed fields can produce undefined behavior.                            | Packed fields cannot be borrowed and require explicit unaligned reads/writes.                                                                          |
| 50  | Manual allocation is listed as unsafe without allocator failure or initialization rules.                                | Raw memory could be treated as initialized typed storage.                                             | Raw allocation returns uninitialized bytes; typed initialization and references require explicit unsafe invariants; safe allocation has fallible APIs. |

## 7. Errors, panic, async, and concurrency

| #   | Source issue                                                                                                         | Why it fails                                                                  | Canonical resolution                                                                                                                       |
| --- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 51  | Typed exceptions have no lowering, ABI, ownership, or destructor model.                                              | Native unwinding and tagged returns have materially different behavior.       | Lower `throws` to tagged success/error control flow with explicit MIR cleanup and no unwinding.                                            |
| 52  | Throwing calls propagate automatically without a source marker.                                                      | Control flow and destructor-triggering early returns are visually hidden.     | Every throwing call requires prefix `try`; throwing awaits require `try await`.                                                            |
| 53  | General union types and error unions share syntax without distinct rules.                                            | Error effects do not behave like ordinary stored union values.                | `throws A \| B` is a closed effect set; ordinary `\|` is limited to optional values.                                                       |
| 54  | Catch syntax and exhaustiveness are described but no propagation rule for partially handled sets exists.             | A catch block could accidentally swallow or leak an error type.               | Catch clauses exhaust the reaching set; a catch body may explicitly throw errors declared by its enclosing function.                       |
| 55  | Native Error subclasses imply heap allocation for every recoverable error.                                           | That cost contradicts systems-oriented error handling and is unnecessary.     | Any value implementing nominal `Error` can be thrown by value; class errors remain possible but explicit.                                  |
| 56  | Assertions disappear in optimized builds.                                                                            | Side effects, validation, and security checks change by profile.              | Assertions always run; profile differences are limited to optimization and debug information.                                              |
| 57  | Async is advertised as zero-cost without pinning, cancellation, or drop-state rules.                                 | Self-referential state machines and canceled resources would be unsound.      | MIR records suspension, borrow checking sees it, lowered futures are pinned, and cancellation drops initialized state once.                |
| 58  | `Promise<T>` is called an alias of a future while typed errors are separate and not carried through stored promises. | Assigning a promise would lose its completion error type.                     | Async signatures retain a compiler-tracked completion error effect; `try await` consumes it.                                               |
| 59  | A built-in executor is promised while examples import and invoke it manually.                                        | Runtime ownership and startup are contradictory.                              | The compiler is executor-neutral; `std/async` provides an explicit executor and `run`.                                                     |
| 60  | Tasks can be spawned without a structured ownership or detach model.                                                 | Borrowed captures may outlive parents and dropped handles may leak work.      | `TaskGroup` owns structured children; dropping a promise cancels; detaching is explicit and requires owned process-lifetime captures.      |
| 61  | Thread examples share state without a language-level capture check.                                                  | Runtime tests cannot compensate for compile-time lifetime and data-race gaps. | Thread and task APIs enforce `Send`, `Sync`, and capture lifetimes.                                                                        |
| 62  | Event-loop platform claims omit wakeups, timers, backpressure, cancellation, and ownership.                          | Naming epoll/kqueue does not define an async runtime.                         | Keep state-machine semantics in the compiler and specify reactor, executor, task, timer, and cancellation responsibilities in `std/async`. |

## 12. Post-implementation decisions

| #   | Source issue                                                                                                                                                                         | Why it fails                                                                                                                                    | Canonical resolution                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 104 | The grammar required an identifier after `@`, but `export` is reserved while `@export` is a required attribute.                                                                      | A conforming lexer cannot tokenize `export` as both an identifier and a keyword based on punctuation.                                           | Add `attribute_name = identifier \| "export"`; `export` is the sole keyword accepted as an attribute name.                                                                                     |
| 105 | `null` was an explicit compile-time error but absent from the keyword table, allowing it to lex as a normal identifier.                                                              | The parser could not distinguish forbidden null syntax from a user value named `null`.                                                          | Reserve `null` as an excluded keyword; it has no grammar production and always receives a localized syntax diagnostic.                                                                         |

## 13. Final decision record

The canonical design therefore commits to:

- a standalone `.tn` grammar and shared lossless syntax tree;
- mandatory ownership and borrow safety with explicit unsafe operations;
- nominal structs, enums, interfaces, and uniquely owned inheritable classes;
- `number` as `isize`, explicit conversions, and checked arithmetic everywhere;
- optional values only through `undefined`, with enums for general sums;
- typed tagged-return errors with explicit `try` and no unwinding;
- executor-neutral async with pinned state machines and structured tasks;
- ordinary standard-library console output;
- raw C ABI plus generated Node-API wrappers as separate products;
- a pinned LLVM 22.1.8 backend;
- macOS ARM64 as the only required host for the current scope;
- a compiler and standard library without package-registry scope; and
- self-hosting validated by deterministic fixed point plus the full independent
  test suite.
